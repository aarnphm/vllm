# A KV cache group in vLLM is one equivalence class that carries a dozen jobs

_A group is the unit of a dozen unrelated jobs, so a split that one job forces is paid for by all the others._

aarnphm asked on 2026-11-19 for every pain point of vLLM's KV cache group machinery, in detail, to design something much simpler and closer to how inference uses memory. Fourteen readers each took one slice of vLLM [`d33bfeef40`](https://github.com/vllm-project/vllm/commit/d33bfeef40edb158ddae320038737ee7923ad66f) (upstream `main` that day). Their reports are in [[research/raw/kv-groups/index]], unedited. Readers ran the real planner, coordinator, managers and connector functions on CPU; nothing here ran on a GPU yet. Where I re-ran a reader's repro myself, the text says so.

Two pages from the same day cover neighbouring ground. [[kv-mess-map]] maps the pain per model family. [[kv-management-design]] proposes four rungs: (1) per-request state rows at the high end of one pool, (2) a free list separate from the eviction list, (3) placement by run, (4) large pages with one owner ([#64401](https://github.com/vllm-project/vllm/issues/64401)). This page maps the group machinery itself and says, for each pain, which rung removes it. Most of what no rung removes is in the last section.

The short version:

- A group is the unit of about a dozen jobs: byte address, tokens per block, allocation policy, block table, prefix-hash unit, eviction scope, admission currency, metadata build, transfer list, draft identity, pool and pipeline stage. Memory and policy rules set the group count, and CPU work pays for it on every step.
- Most memory waste comes from one rule: every group aliases one byte space at one page size. One group with mixed page sizes wastes nothing. The rule costs 32% of the planner's code, 4% to 52% of each state page as padding, 11% to 21% idle layer slots (Gemma 3; Kimi-K3 with a draft), 7.2× the needed bytes for a small drafter, and it pushes Kimi-K3's attention block at TP4 to 1,536-3,200 tokens (24× to 50× the kernel block, depending on KV dtype and drafter), which coarsens prefix hits, window frees and P/D ratios. At 128k context the padding is under 3% of KV memory on every model measured; the cost shows up as inflated blocks, at short context (8k: 3% to 30% on state hybrids), and with drafters (91% for Kimi-K3 with a DSpark draft, 11.6× fewer concurrent requests than exact-size pools).
- One LRU queue for all groups strands cached prefixes: 6.0% real hit rate where the full-attention group alone held 29.0%. Most of that gap is junction re-detection lag. Remembering junction positions and giving mid-request frees their request's end time recovers 87-112% of it in simulation; a separate free list (rung 2) changes nothing.
- The planner writes the byte layout and five of seven layout-aware connectors rebuild it from tensor strides: about 8.5k lines. SimpleCPU uses the planner's layout in 125 lines (22:1).
- vLLM's own concurrency estimate, which feeds startup admission and `--max-model-len auto`, is 2× to 8× below what the manager admits on every multi-group model.
- On GB300 with CUDA graphs, attention-metadata building is about 6% of a decode step's host time at 1 group and about half at 8-10 state groups (Nemotron-H, Granite-4-H). Every GPU-resolved plan (13 models) matches the CPU planner exactly.
- 24 bugs, 19 of them reproduced on CPU. Bugs 2 to 5 give wrong output silently; bug 1 crashes the scheduler on a partial hybrid prefix hit with full KV-event reports (public issue #63149, open fix #57358). Upstream history: 472 KV-group bugs in 9.5 months, 40% silent, the monthly count up 8×.
- The four rungs of [[kv-management-design]] fix the memory model (causes 1 to 3 and part of 8). Rung 2 does not touch the eviction gap of cause 6; junction memory and request-end recency do. Block-table ownership, the layout contract with peers, policy as data, and metadata per group stay open.

## What a group is

A group (`KVCacheGroup`, [`vllm/v1/kv_cache_interface.py:688-805`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/kv_cache_interface.py#L688-L805)) is a set of layers that share one block table. Its fields: the layers' specs, one `ManagerConfig` (the allocation policy, a `SingleTypeKVCacheManager` subclass plus frozen `Params`), `block_size` in tokens, `dcp_sharded`, `is_eagle_group`, `host_resident`, `enable_kv_transfer`, `role`, `unprojected_specs`. `KVCacheGroup.from_layers` asserts the layers agree on policy, block size and DCP ([`:722-728`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/kv_cache_interface.py#L722-L728)).

All groups draw block ids from one `BlockPool` and alias the same bytes: the planner's comment reads "Groups alias from byte 0", and each group's `byte_offset` restarts at 0 ([`kv_cache_planning.py:639`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/kv_cache_planning.py#L639), [`656`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/kv_cache_planning.py#L656)). `bytes_per_block` is the largest group's page ([`:542-559`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/kv_cache_planning.py#L542-L559)) and `num_blocks = available_memory // bytes_per_block` ([`:635`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/kv_cache_planning.py#L635)), so a block id costs the largest page in every group. The `KVCacheTensor` docstring states the bargain: "cache groups overlay each other, which is sound because a block ID is owned by one group at a time" ([`kv_cache_interface.py:645-647`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/kv_cache_interface.py#L645-L647)).

The group is the unit for each of these jobs. Each row says what decides the job today and what a split costs.

| Job                      | Decided by                                                              | Cost when two layers differ                                         |
| ------------------------ | ----------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Byte address of a block  | `id × bytes_per_block`, all groups from byte 0                          | pages must be equal: padding, block inflation, idle layer slots     |
| Tokens per block         | ~16 sites across 3 processes (planner reader)                           | the largest page sets every group's block size                      |
| Allocation policy        | one manager per group                                                   | 118 `isinstance` checks on manager classes in 32 files              |
| Kernel addressing        | one block table per group; kernel block chosen in 4 places, held 3 ways | block-table width computed two ways (a reproduced crash)            |
| Prefix hash and hit unit | `hash_block_size` = gcd, alignment = lcm of group block sizes           | hits round to the coarsest group                                    |
| Eviction                 | one LRU queue for all groups                                            | windowed and state tails evicted before the prefixes they pair with |
| Admission                | one block currency, sentinel `num_gpu_blocks + 1`                       | head-of-line block for the whole step                               |
| Per-step metadata        | one backend build per group                                             | 1,032 CUDA API calls per step at 46 groups ([#58762](https://github.com/vllm-project/vllm/issues/58762))                 |
| Per-step manager work    | every allocation calls every group                                      | 2.4 µs → 32.4 µs per request, 1 → 27 groups (CPU)                   |
| Transfer                 | per-group block-id lists; connectors rebuild the layout                 | ~8.5k lines of translation in connectors                            |
| Draft identity           | `is_eagle_group`, `is_draft`                                            | 123 drafter-involved bugs                                           |
| Pool membership          | `host_resident`, `role` (HiSparse)                                      | a second planner with ~12 special cases                             |
| Pipeline stage           | `unprojected_specs`; scheduler sees stage 0                             | equal `num_blocks` strands memory on other stages                   |

The group count is therefore set by memory rules (equal pages) and policy rules (one block table), and charged by CPU rules (one build and one manager call per group per step). Upstream proposals trade between them: [#58207](https://github.com/vllm-project/vllm/issues/58207) offered 30% of KV capacity for fewer groups.

## The pain, by root cause

Ordered by how much of the rest each one causes. Each cause gives its evidence, then the rung of [[kv-management-design]] that removes it, if any. Numbers carry the reader who produced them; "re-run here" marks the ones I ran again.

### 1. Every group aliases one byte space at one page size

A block id names the same byte range in every group, and one `num_blocks` and one null block (id 0) serve all groups. So every group's page must be equal, and the planner forces it three ways: it pads pages, it raises the attention block size until one attention page holds the largest state page, and it splits layer buckets into equal-size groups with idle layer slots ([`kv_cache_planning.py:493-530`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/kv_cache_planning.py#L493-L530), [`542-559`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/kv_cache_planning.py#L542-L559)). The planner reader found that one group with mixed page sizes is legal and wastes nothing; the MLA plus sliding-window fallback already builds one ([`kv_cache_planning.py:785-796`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/kv_cache_planning.py#L785-L796)). The padding, the inflation and the idle layer slots all come from groups sharing bytes. (Spec-decode scratch is a separate waste, cause 3.)

- Block inflation: Kimi-K3 at TP4 gets 1,536-token attention blocks with default flags, 2,944 with the fp8 recipe flags and 3,200 with fp8 and an 8-token DSpark draft (probe), and 1,792 with a bf16 SSM state and 8 draft tokens (planner). Qwen3-Next at TP4 gets 320, Nemotron-Nano-9B-v2 1,344 at every TP (probe). The bug history shows attention blocks from 528 to 7,808 tokens.
- Padding: state pages carry 4-16% padding (planner). Qwen3-Next at TP8 pads 43% of every GDN state page (state). Qwen3-Next at TP4 pads 19.4% because the hybrid block is aligned to 64 tokens; aligned to 16 it would pad 1.5% (planner).
- Idle layer slots: Gemma-3-27B gets 7 groups with 11.4% idle slots, +12.9% memory per request at 8k. Kimi-K3 with a same-dtype 5-layer DSpark draft puts the draft in the MLA bucket, so every KDA block carries 20.7% idle slots: 162 MiB idle against 24.6 MiB of real draft KV per request (6.6:1) (planner).
- Drafters: a 5-layer DFlash group uses 13.9% of each block, 7.2× what it needs, and capacity falls 28.9% at 4k context and 9.6% at 16k (bends). A bf16 MLA draft next to the fp8 K3 target gives 20 groups, 52% padding on every KDA page and +62% memory per request at 32k, with no warning (planner). Upstream [#62558](https://github.com/vllm-project/vllm/issues/62558) reports a pool falling from 235k to 97k tokens by the same mechanism.
- Safety: freed pages pass between groups of different dtypes. Any Mamba layer therefore forces zeroing of every new attention block ([`kv_cache_interface.py:885-888`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/kv_cache_interface.py#L885-L888)), and a uint8 indexer does the same for DSA models (spec). The bug history has 11 NaN bugs from this reuse; bug 5 below is the same family.
- Pipeline parallelism: every stage gets the same `num_blocks`. A synthetic K3 PP4 plan leaves 8.57 of 60 GiB unused on three stages; Gemma 3's idle slots rise from 11% to 24-29% at PP4 (planner).
- Code and failures: about 580 of the planner's 1,790 lines (32%) and 548 platform lines exist to keep pages equal (planner). 35 startup crashes in 9.5 months trace here (bugs).

Removed by: rung 1 for state, rung 4 ([#64401](https://github.com/vllm-project/vllm/issues/64401)) for token kinds with unequal pages, a draft pool ([#64611](https://github.com/vllm-project/vllm/issues/64611)) for drafters. Rungs 2 and 3 leave it.

### 2. The block in tokens does six jobs, so inflating it degrades all six

`KVCacheGroup.block_size` is the allocation quantum, the prefix-hash and hit unit (gcd and lcm over groups), the state checkpoint interval, the granularity of window frees, the P/D block ratio and the base of the kernel-block split. Cause 1 inflates it, and each of the other jobs gets coarser with it.

- Prefix hits recompute B/2 tokens on average: 896 for K3 at TP4 with bf16 state, 1,600 with fp32. RFC [#66844](https://github.com/vllm-project/vllm/issues/66844) shows 1,796 of 2,096 prefilled tokens recomputed on a second turn (state).
- A 128-token window holds 144 token slots at block 16 and 1,088 at block 544 (8.5×); a resent prompt recomputes 8.5 tokens against 271.5 (managers).
- In Mamba `none` mode with any connector, the hash unit becomes lcm(block, `max_model_len`): 1,310,720 tokens for Qwen3-Next at TP4, so connectors never see a block hash ([`kv_cache_utils.py:860-866`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/kv_cache_utils.py#L860-L866), state).
- `extract_hidden_states` turns the target's scheduler and hash block sizes from (16, 16) into (64, 1), and hashing an 8k prompt gets 8.1× slower ([`kv_cache_planning.py:1019-1053`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/kv_cache_planning.py#L1019-L1053), bends).
- About 16 places in three processes decide the number (planner). The platform runs a shadow planner after model load that re-derives every page from config: 7 probe specs and 1,026 lines of model helpers against 714 lines of real producers (spec). The two derivations disagree already: 656 B per token in the probe against 528 B for the SM120 sparse MLA layer ([`platforms/interface.py:1021`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/platforms/interface.py#L1021) against [`mla_attention.py:1647`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/model_executor/layers/attention/mla_attention.py#L1647)). The kernel block size is chosen in 4 places and stored 3 ways (runner); kernel sizes are negotiated at about 18 sites in 9 files (backends); DCP-scaled block sizes are derived in at least 8 places (bends). `cache_config.block_size` is collapsed to the minimum over groups ([`core.py:362`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/engine/core.py#L362); 10 bugs), and overwriting it after init gave NaN logits at TP1 ([#60252](https://github.com/vllm-project/vllm/issues/60252)).

Removed by: rung 1 sets the token block to the kernel quantum (128 on K3 at any TP), which ends the inflation. No rung separates the hash unit from the allocation unit.

### 3. Per-request state has no object of its own

A recurrent state, a conv window, a ring and a compressor state each have a fixed size per request. vLLM stores each as pages of a token-block pool, in three encodings of the same object: `MambaSpec`, `CircularBufferSpec`, and a sliding window of 4 tokens ([[kv-mess-map]]).

- Memory: K3 at TP4 with 8 draft tokens and the default fp32 recurrent state holds 1,392 MiB of state per request against 117 MiB needed (11.9×), 11× its attention KV at 8k. Across the corpus, state takes 3.6-11× the attention KV at 8k with spec decode; Qwen3-Next is the exception at 0.4-1.2× (state).
- Spec scratch: one full state page per draft token for the life of the request ([`mamba/abstract.py:115-121`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/model_executor/layers/mamba/abstract.py#L115-L121)), 1,012 MiB per request for K3 at TP4 with 8 draft tokens. GDN reserves 2 + k blocks per layer, and no draft-pool proposal touches it.
- Modes: `mamba_cache_mode` is a pure function of `enable_prefix_caching` ([`models/config.py:1315-1336`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/model_executor/models/config.py#L1315-L1336)), yet it has 66 references in 33 files plus 45 derived predicates; the PR that removes it ([#63830](https://github.com/vllm-project/vllm/issues/63830)) touches 110 files. Align mode nulls and relocates block-table entries, so connectors read state through three side channels.
- A second allocator: the Mamba manager is 899 lines, 117 of the file's 247 branches and 10 per-request maps. Its block estimate and its allocator are near copies that already disagree ([`single_type_kv_cache_manager.py:2306`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/single_type_kv_cache_manager.py#L2306) against [`:2392`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/single_type_kv_cache_manager.py#L2392)), and 18 of 42 bug fixes in a year touch it (managers). The checkpoint-position rule is computed in 5 or more places with different inputs (state).
- P/D: conv rows depend on `num_speculative_tokens`, and NIXL's compatibility hash leaves it out, so P and D with different draft lengths exchange conv state at the wrong offsets with no error (bug 3). Mooncake pairs state slots from the tail without dropping scratch slots (bug 4).

Removed by: rung 1 (state rows) for the size class, the padding and the block-size coupling. Scratch is a lifecycle fix that exists as a flag (ReplaySSM). Prefix-caching checkpoints in rows are designed in rung 1 and not yet simulated.

### 4. Block tables are positional arrays per group, with no ownership

A block-table row maps token position to block id for one group. A freed block can only become a null entry, the worker receives only appended ids, and a block id carries no group tag.

- Waste and cost: at 128k a sliding-window row has 8,192 entries for 9 live blocks, kept in up to five copies, so 126:1 to 910:1 of the entries are dead (runner). A miss on a 1M-token prompt costs that group 65,535 hash lookups, about 10 ms, against 1 for full attention (managers).
- Staleness: the scheduler's frees never reach the worker. The worker re-derives dead entries for sliding windows only ([`gpu/block_table.py:325-339`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/worker/gpu/block_table.py#L325-L339)), so R-SWA's freed middle gap stays in the worker's table and FA4 reads it (bug 5).
- Identity: block ids live in 7 index spaces with 3 wire orders, and Mooncake and MoRIIO guess the space from list length. Load failures carry no group, so the scheduler refuses block-level failures on multi-group models and recomputes from token 0 ([`scheduler.py:3878`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/sched/scheduler.py#L3878), [`3891`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/sched/scheduler.py#L3891)): one bad block of a 128k prompt costs 8,192 blocks of recompute (connectors). Async connectors cannot tell a reused id from the old one ([#62810](https://github.com/vllm-project/vllm/issues/62810), no replies).
- Bug history: 66 bugs trace to block tables kept per request slot with no ownership across 7 layouts, 14 to the null block and stale rows, 28 to block-table or view memory faults (bugs).

Removed by: no rung. The nearest reference is SGLang's request table of virtual ids, translated per sub-pool once per iteration (see Other engines).

### 5. The planner records the layout, and the consumers ignore it

The planner already writes `KVCacheTensor(offset, layer_stride, block_stride)` per set of layers. Five of the seven layout-aware connectors rebuild it from `stride()` and `shape`, and the backends keep the page interior private.

- Size: about 8.5k connector lines translate vLLM's group and layout data, 2,772 of them in NIXL (38% of NIXL). SimpleCPU reads the planner's layout directly in 125 lines (22:1), and UMBP does the same. Connector code has 289 branches on group or spec kind in 61.5k lines; "is this Mamba?" has 6 encodings at 50 sites; `use_mla` is read 67 times against 3 reads of the planner's replication facts (connectors).
- Agreement: NIXL makes peers agree through a 302-line validator over 22 metadata fields ([`nixl/base_worker.py:2892-3193`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/distributed/kv_transfer/kv_connector/v1/nixl/base_worker.py#L2892-L3193)). Its compatibility hash leaves out the grouping and `num_speculative_tokens`, and production K3 lanes turn the hash off ([[kimi-k3-reference]]). Every TP-slicing PR derives the peer's spec by scaling the local one ([#65232](https://github.com/vllm-project/vllm/issues/65232), [#67559](https://github.com/vllm-project/vllm/issues/67559), [#66837](https://github.com/vllm-project/vllm/issues/66837)); none sends the spec (upstream).
- Per-group facts collapse to engine-wide scalars: `TransferTopology` holds one block size, one MLA flag and one KV-head count ([`kv_connector/utils.py:559-576`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/distributed/kv_transfer/kv_connector/utils.py#L559-L576)); NIXL picks one kernel block size for all groups while the runner picks one per group (connectors).
- Interior: the `N × C` interior is private to at least six backends. Consumers guess the format from tensor shape ([`offloading/canonical_mapping.py:260-263`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/distributed/kv_transfer/kv_connector/v1/offloading/canonical_mapping.py#L260-L263)), and the NVFP4 writer and reader disagree under LBNHC (measured). K/V content has five encodings; the quant format has five identities, with 196 string comparisons on the dtype against 76 reads of `KVQuantMode`. One layout per model is chosen by vote ([`backends/utils.py:312-430`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/attention/backends/utils.py#L312-L430)), and ROCm drops its native kernels without a log line when a connector or a hybrid model is present (backends).
- Bug history: geometry rebuilt by connectors accounts for 115 bugs, and a connector is involved in 186 (bugs).

Removed by: no rung. See the section on logical TP slicing.

### 6. One queue is the free list, the eviction order and the cache index

`BlockPool.free_block_queue` is one LRU list for every group, ordered by release time. It puts unhashed blocks at the front and hashed blocks at the back ([`block_pool.py:826-837`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/block_pool.py#L826-L837)).

- Stranding: sliding-window and Mamba tails are released mid-request, so they are evicted before the full-attention prefixes they pair with. In a 700-block simulation on the real coordinator the hit rate was 6.0%, while the full-attention group alone held enough for 29.0%; 85% of the cached full-attention prefix blocks, half the pool, were unusable (coordinator).
- Retention: under the default retention a sliding-window group keeps no decode state, while Mamba keeps one on free. A second turn recomputes 716 tokens instead of 108 (6.6×) (managers).
- Order: the immediate and deferred free paths use different orders. "every fix ... is another hard-coded reordering of that queue" (yubofredwang, [#64150](https://github.com/vllm-project/vllm/issues/64150)). Four open PRs reorder it ([#48532](https://github.com/vllm-project/vllm/issues/48532), [#63851](https://github.com/vllm-project/vllm/issues/63851), [#55841](https://github.com/vllm-project/vllm/issues/55841), [#62810](https://github.com/vllm-project/vllm/issues/62810)), and none separates the three jobs.

Measured on the real `KVCacheManager` with policies swapped into `BlockPool` (eviction reader, `reports/evict.md` in [[research/raw/kv-groups/index]]; FA + SWA-128 and FA + Mamba align, 3 seeds, multi-turn 10 seeds):

- Rung 2 changes no number on any of 48 runs, because today's queue already hands out every unhashed free block before it evicts a cached one ([`block_pool.py:826-837`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/block_pool.py#L826-L837)).
- Evicting a cached prefix as one unit across kinds recovers 10% of the gap at 700 blocks and 27% at 1,400 on FA + SWA (6.0% → 8.2%, 25.2% → 32.0%), 8% and 58% on FA + Mamba. It also regresses in two ways: a hot primary keeps its duplicate copies cached, and hot FA blocks keep cold SWA members cached (multi-turn 44.2% against 47.1% today).
- About 17% of the gap is a window or state block evicted while its FA chain stays cached, which is all that coupling can recover. About 70% is junction re-detection lag: under the default retention, the window tail or Mamba state at a shared-prefix junction is written only when a lookup sees the FA hit exceed the other group's hit, so once both are evicted the next request rewrites only the FA chain and the request after it misses again.
- What closes it: remember junction hashes so the boundary state is rewritten on the next pass (alone: 38% of the gap at 700 blocks, 88% at 1,400), plus request-end recency for blocks freed mid-request and dropping duplicate copies. Together that reaches 26.1% at 700 blocks and 52.9% at 1,400 (87% and 112% of the gap; above 100% because junction memory also raises the FA-only rate), 88% and 110% on FA + Mamba, with admission unchanged.
- Upstream: [#63851](https://github.com/vllm-project/vllm/issues/63851), ported line for line, recovers -4% to 1% here, because its `drop_unreachable_tail` uncaches FA chains that sibling requests need to detect junctions; it is the best policy on multi-turn (49.1% against 47.1%). [#48532](https://github.com/vllm-project/vllm/issues/48532) only reorders the deferred free path and equals today.

Removed by: no rung as written. The fix is a retention rule (junction memory) plus an eviction-order rule (request-end recency), both inside today's single pool.

### 7. Policy lives in class identity, flags and overloaded hooks

- 221 dispatch sites test spec, manager or `Params` classes (spec). 10 of the 18 MLA-family specs are indexers, fp32 compressor state or hidden states that subclass MLA to get sized.
- Spec equality covers every field, so incidental fields split groups. IndexCache leader and skip layers differ only in `is_index_group_leader` and get an extra metadata group and split prefix lookups; HY-V4 strips fields by hand before comparing (spec).
- Hooks change meaning per subclass: `get_num_blocks_to_allocate` returns a count, a sentinel or 0. The sentinel `num_gpu_blocks + 1` means "not now", and the waiting loop breaks on it ([`scheduler.py:1518-1525`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/core/sched/scheduler.py#L1518-L1525)), so one request stops admission for the whole step (coordinator, managers, state).
- The EAGLE drop is a whole-request rule stored as per-group flags; `use_eagle` has five meanings; draft identity has four sources (bends). EAGLE plus chunked local turns the hybrid manager off ([`config/vllm.py:2344-2354`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/config/vllm.py#L2344-L2354)), so Llama-4's local layers are allocated as full attention: 3.4× the memory per request at 128k on Llama-4-Scout at TP4 (6,144 against 1,824 MiB, probe). The warning next to it still says the hybrid manager is disabled "by default" for chunked local attention, while the switch defaults to on ([`envs.py:2097-2098`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/envs.py#L2097-L2098)); one reader was misled by it.
- HiSparse is a second KV system (3,647 + 485 lines) with an early return in every planning entry point (bends). Per-model runner behaviour lives in `ModelState` subclasses that cannot be combined (runner).
- A reservation that existed only as a constructor side effect was deleted as dead code (bug 2). R-SWA and cross-attention report themselves as prefix-cacheable and rely on model config to turn caching off, so an explicit `--enable-prefix-caching` crashes encoder-decoder models (bug 13).
- One connector class without HMA support turns the hybrid manager off for the whole engine ([`config/vllm.py:2366-2389`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/config/vllm.py#L2366-L2389)).

Removed by: no rung. TRT-LLM's lifecycle registry declares policy as data (see Other engines).

### 8. The group count is paid on every step

- One backend metadata build runs per group ([`gpu/attn_utils.py:513-593`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/worker/gpu/attn_utils.py#L513-L593)), with build reuse for Mamba groups only. [#58762](https://github.com/vllm-project/vllm/issues/58762) measured 1,032 CUDA API calls per step at 46 groups; [#52297](https://github.com/vllm-project/vllm/issues/52297) quotes about 900 µs per GDN build against 20 µs for FlashAttention (45:1). The GPU check below measured 100-116 µs for a full GDN build and 46-57 µs for a FlashInfer build on GB300, about 2:1, with reused Mamba builds at 12-18 µs. The runner's own loop is 1.1 µs per group, so the cost sits in the builds (runner, upstream).
- Every allocation calls every group: 2.4 µs per request at 1 group, 32.4 µs at 27, about 5.2 ms per step for 160 decodes on CPU (managers). The coordinator measured 2.39 → 9.59 µs per request from 1 to 6 groups. [#66903](https://github.com/vllm-project/vllm/issues/66903) reports −16% TPOT on DeepSeek-V4 with HiSparse (27 groups) from skipping idle groups.
- A degenerate case: an MTP drafter set to DCP 1 under a DCP target turns a 61-layer MLA model into 62 one-layer groups (bug 14). The trigger is opt-in: the draft inherits the target's DCP unless `draft_decode_context_parallel_size=1` is set, and [#68533](https://github.com/vllm-project/vllm/pull/68533) tests the split as intended. At DCP 8 with 8K prompts, admission costs 0.522 ms per request against 0.010 ms when the draft runs at the target's DCP. The pool takes 1.95 s against 0.01 s to build and 563 MiB against 9 MiB of heap. An earlier figure here (68.9×, 6.9 s) ignored DCP scaling and was timed with tracemalloc on (corrected 2026-11-20).
- The weakest group sets the CUDA graph mode for the whole model, drafter groups included (runner).
- [#58207](https://github.com/vllm-project/vllm/issues/58207) offered 30% of KV capacity to get fewer groups.
- Measured on GB300 (GPU check below): metadata host time per step grows from 46 µs at 1 group to 786 µs for Granite-4-H's 10 groups and 2.9 ms for Llama-4-Scout, whose 3 chunked-local groups each rebuild the same chunk metadata. Granite's 9 state groups exist only to equalize pages and cost about 670 µs per step, where one state group would cost about 166 µs. With CUDA graphs on, metadata building is about 6% of the host-side `execute_model` time at 1 group, 14-20% at 4-7 groups, and 42-54% at Nemotron-H's 8 and Granite-4-H's 10 groups.

Removed by: rung 1 removes the state groups (K3 from 4 to 1, from 20 to 6 with a drafter). Token-kind groups stay ([#58207](https://github.com/vllm-project/vllm/issues/58207), [#58380](https://github.com/vllm-project/vllm/issues/58380)). No rung builds metadata once per (backend, kernel block) instead of once per group.

### 9. Planning spans three processes and is edited after the fact

- `KVCacheConfig` leaves the planner incomplete: the engine core fills in the layout and hash fields ([`core.py:341`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/engine/core.py#L341), [`387-389`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/engine/core.py#L387-L389)), the Mooncake store rewrites the retention interval, and `resolve_kv_cache_block_sizes` runs at 8 call sites (planner).

- Startup planning counts 2.4-2.6× fewer blocks per request than runtime admission ([#50169](https://github.com/vllm-project/vllm/issues/50169), upstream).

Removed by: no rung.

## Other engines

The peers reader read SGLang ([`6515ac29`](https://github.com/sgl-project/sglang/commit/6515ac29d3c2206ec4a9b54c40e6b2b25c3a43a3)), TensorRT-LLM ([`0e929baf`](https://github.com/NVIDIA/TensorRT-LLM/commit/0e929bafa006b76e090a5df88f08c0b1b6a6fa32)), Dynamo (`51ae4a04`) and LMDeploy (`d9585066`). Both large peers redesigned hybrid KV memory around the same idea: declare each cache by its lifetime with exact geometry, and give caches with the same slot signature a shared free list. They differ in how memory moves between the pools that result.

|                 | vLLM                            | SGLang unified memory (off by default)                                                                     | TRT-LLM KVCacheManagerV2 (opt-in)                                       |
| --------------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Allocation unit | one padded page for every group | exact page per band                                                                                        | exact slot per lifecycle                                                |
| Pools and split | one pool, uniform pages         | one `uint8` arena, one band per lifetime; bands grow from both ends, middle bands float                    | a CUDA VMM range per pool group over one shared pool of physical chunks |
| Rebalancing     | none needed (one size)          | lazy compaction moves pages; capacity shifts every iteration                                               | auto-tuner at most every 120 s, stop-the-world, 21.1 ms                 |
| Request table   | one positional table per group  | virtual ids, translated per sub-pool once per iteration                                                    | one table per lifecycle, one conversion kernel per step                 |
| Cost            | padding, inflation, groups      | page-hazard ledger, write-after-read barrier, 10.3k-line allocator (1.09× vLLM's whole `v1/core` KV stack) | refused under disaggregation, KV connectors and drafters                |

Both peers' default stacks split memory statically at boot. SGLang's docs show that moving that one split changed the prefix hit rate from 0.06 to 0.89 and throughput 4.8× at equal memory; in [sglang#49676](https://github.com/sgl-project/sglang/issues/49676) a static split left about 90% of one pool unused. That is the case for vLLM's fungibility, and the reason not to adopt a static split.

## Logical TP slicing first, physical blocks second ([#67559](https://github.com/vllm-project/vllm/issues/67559))

aarnphm pointed at [#67559](https://github.com/vllm-project/vllm/issues/67559) ("[KV Connector] Spec-driven TP slicing for NIXL", ZhanqiuHu, a port of Lucas's [#65232](https://github.com/vllm-project/vllm/issues/65232)): describe how a cache splits across TP ranks as arithmetic on the spec, then apply it to physical blocks. The tpslice reader fetched the PR head ([`f2fc45b9b7`](https://github.com/vllm-project/vllm/commit/f2fc45b9b79d4020fcf7cda15a7f83a6412618e7), merge base [`52fae19fb6`](https://github.com/vllm-project/vllm/commit/52fae19fb648cea2d0fdfbf1e9cdcfedacc3c4ca)), ran its slicing on 46 cases and compared every byte against real pages built on CPU.

How the PR works:

- `KVCacheSpec.slice_for_tp_transfer(cache, tp, rank, other_spec, other_tp, other_rank, receiving)` returns views of one page (post-PR [`kv_cache_interface.py:270-296`](https://github.com/vllm-project/vllm/blob/f2fc45b9b79d4020fcf7cda15a7f83a6412618e7/vllm/v1/kv_cache_interface.py#L270-L296), [`523-564`](https://github.com/vllm-project/vllm/blob/f2fc45b9b79d4020fcf7cda15a7f83a6412618e7/vllm/v1/kv_cache_interface.py#L523-L564), [`667-728`](https://github.com/vllm-project/vllm/blob/f2fc45b9b79d4020fcf7cda15a7f83a6412618e7/vllm/v1/kv_cache_interface.py#L667-L728)).
- Attention: KV-head positions are numbered across all of a side's ranks, $S = tp \cdot n$, a replicated head counted once per rank. Receiving position $h$ reads sending position $\lfloor h \cdot S_{send} / S_{recv} \rfloor$.
- Mamba: row intervals are intersected per state segment (x/B/C, Q/K/V, temporal heads), and backend subclasses declare the segments.
- NIXL builds a `(1, H, N_k, C)` int8 meta page per side in the layout's stride order and slices both. `contiguous_byte_ranges` turns each pair of views into (local, remote, bytes) runs, and region base plus block stride times block id gives the addresses.
- Peer geometry: only KV heads per layer cross the wire. Everything else is copied from the local spec, and Mamba shapes are scaled by the TP ratio (post-PR [`nixl/base_worker.py:245-269`](https://github.com/vllm-project/vllm/blob/f2fc45b9b79d4020fcf7cda15a7f83a6412618e7/vllm/distributed/kv_transfer/kv_connector/v1/nixl/base_worker.py#L245-L269)).

What the bytes show:

|                                   | main | [#67559](https://github.com/vllm-project/vllm/issues/67559)                     |
| --------------------------------- | ---- | -------------------------- |
| Cases that corrupt data, of 46    | 9    | 4                          |
| Outcomes the PR fixes / regresses |      | 13 / 3                     |
| NIXL production lines             |      | −780 (validator 302 → 155) |
| Spec lines                        |      | +276                       |

Every PR corruption traces to the guessed peer spec, and passing the true remote spec turns all four into refusals.

1. K/V-plane backends (`num_head_slots=2`: b12x, ROCm): a size test decides that dim 1 is heads, and the remote slot count is scaled. When a rank holds exactly two heads, 168 to 232 of 384 bytes land wrong with no error. `main` is wrong here too.
2. Mamba2 with replicated groups (`n_groups=1`): the "does not shard evenly" guard cannot fire against a scaled spec, and the length check is skipped for padded pages. Hybrid models pad the Mamba page whenever it differs from the attention page, so hybrids corrupt silently. The PR's fail-closed test passes the true spec, so it never reaches this path.
3. A padded attention page with a remote holding more heads: the copied `page_size_padded` raises `AssertionError` at handshake. `main` corrupts this case silently.
4. Regression: H2ND pages (`kv_head_major_slots`, MiniMax-M3 NVFP4) are refused. `main` supports them ([#64475](https://github.com/vllm-project/vllm/issues/64475)), and the PR deleted those tests.
5. Runs merge in logical axis order, so layouts with tokens outside heads (NHD) get 4× more runs: 64 instead of 16 per block at 8 KV heads and head size 128.

The PR adds support for NHD layouts at different TP, FlashInfer NVFP4, replicated-prefill GQA (which `main`'s validator asserts away) and unaligned Mamba state, and it handles drafts generically. No human has reviewed [#67559](https://github.com/vllm-project/vllm/issues/67559), [#65232](https://github.com/vllm-project/vllm/issues/65232) or [#66837](https://github.com/vllm-project/vllm/issues/66837); all three are drafts with merge conflicts, and no GPU run of a hybrid model across TP sizes exists.

The minimal core that the measurements support has three parts.

- **What each side sends, per page piece:** an offset; named axes (name, size, stride); its shard interval in unsharded units (axis, first, count, total). Region base, block stride, block count and kernel split already cross the wire.
- **`moved`:** intersect the two intervals; among replicas, the sender is `recv_rank · send_tp / recv_tp`.
- **`narrow`** shifts the offset and cuts the size; **`runs`** merges the pair's axes in stride order.

That is [#67559](https://github.com/vllm-project/vllm/issues/67559) with three changes: named axes replace the size test, intervals sent by each side replace the scaling, and stride order replaces logical order. Against the earlier prototype ([[kv-layout-algebra]]), it keeps `take`, `fix` and `split` and the sorted merge, carries pieces as data instead of spec subclasses, and drops `complement`, as aarnphm's review asked. With rung 1, a request's state row is one piece with one interval: one run per request. This is the payload that cause 5 is missing, and it is small enough to put in the handshake.

## Kernels and CUDA graphs: where the grouping heuristic lands

aarnphm asked how the groups, and the heuristic that forms them, play into the kernels and CUDA graph capture. A reader traced the MRV2 path at [`d33bfeef40`](https://github.com/vllm-project/vllm/commit/d33bfeef40edb158ddae320038737ee7923ad66f) against the GPU runs above (`reports/graphs.md` in [[research/raw/kv-groups/index]]).

**From groups to kernels.** Each KV group is split into attention groups by (backend, spec, query heads), and each attention group has its own metadata builders ([`gpu/attn_utils.py:540-561`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/worker/gpu/attn_utils.py#L540-L561)). Each group gets its own kernel block size and its own persistent buffers: two `[max_num_reqs, W]` block tables, a slot-mapping row, a kernel-block table when manager blocks are split, and the builders' buffers. The attention kernels themselves run once per layer whatever the grouping; a group decides which block table, kernel block size and metadata a layer's kernel receives. No kernel reads more than one group's table.

**From groups to CUDA graphs.**

- The graph mode is the minimum `AttentionCGSupport` over every attention group, draft layers included ([`gpu/attn_utils.py:314-339`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/worker/gpu/attn_utils.py#L314-L339), resolved in [`config/compilation.py:1576-1725`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/config/compilation.py#L1576-L1725)). One builder at `NEVER` removes FULL graphs for the whole model. The chunked-local wrapper is forced to `NEVER` ([`chunked_local_attention.py:42-50`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/model_executor/layers/attention/chunked_local_attention.py#L42-L50)), so Llama-4-Scout's 12 full-attention layers lose FULL graphs too.
- Graphs are keyed by batch shape, not by group: on SM100, 37 FULL decode graphs and 54 PIECEWISE graphs (Granite captured both sets in 16 s). Every graph contains every group's kernels, so capture time and graph memory follow model size, not group count (table in the GPU check). A FULL graph bakes in each group's buffer addresses and block-table widths, and a FULL capture builds metadata twice per graph ([`gpu/cudagraph_utils.py:500-523`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/worker/gpu/cudagraph_utils.py#L500-L523)).
- At every replay the host still builds metadata for every group ([`gpu/model_runner.py:2071-2082`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/worker/gpu/model_runner.py#L2071-L2082)). The FULL graph reads only the block-table gather, the slot mapping and a few per-group writes (state-index copies, the kernel-block expansion). On GB300, FlashInfer's trtllm-gen decode build writes nothing that the graph reads. So most of the per-group host cost measured above is work whose output a FULL decode graph never reads.

**What is really per group.** For groups of one (backend, policy, block size), such as Gemma-3's 6 sliding-window groups, Granite's 9 Mamba2 groups and Llama-4's 3 chunked-local groups, the builders recompute the same decode/prefill split, sequence lengths, scheduling plan and chunk metadata. Only the block-table pointer, the slot mapping and, for state, the state indices differ.

- Reuse through `update_block_table` is gated to `MambaSpec` groups ([`gpu/attn_utils.py:563-591`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/worker/gpu/attn_utils.py#L563-L591)). FlashAttention and B12X implement it but are excluded; FlashInfer, the attention backend of every group in this corpus on GB300, has none. KDA builders never reuse ([`gdn_attn.py:210-214`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/attention/backends/gdn_attn.py#L210-L214)), and any speculative decoding turns Mamba1/2 reuse off ([`mamba_attn.py:197-199`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/attention/backends/mamba_attn.py#L197-L199)).
- A Mamba2 "reuse" costs 82-125 µs with graphs, against 30-37 µs for GDN, because Mamba2 never uses the state indices that `MambaHybridModelState.prepare_attn` computes for all groups in one launch ([`gpu/model_states/mamba_hybrid.py:303-317`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/worker/gpu/model_states/mamba_hybrid.py#L303-L317)). Each Mamba2 group pays its own Triton launch, two dataclass copies, and a copy plus fill into the graph buffer ([`mamba_attn.py:664-703`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/attention/backends/mamba_attn.py#L664-L703)).
- Llama-4's chunked-local groups each rebuild the same virtual batch, including a blocking `seq_lens.cpu()` ([`backends/utils.py:632-759`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/attention/backends/utils.py#L632-L759)). The first group absorbs the GPU queue, which is the 2-14 ms; the others cost 0.4-0.5 ms. FlashInfer's own builder avoids that sync with `seq_lens_cpu_upper_bound`. The same virtual batches can outnumber `max_num_seqs` (bug 24).

Persistent block-table buffers are small either way (Gemma-3: 43 MiB today, 12 MiB merged, against 60 GiB of KV per GPU), so the cost of the extra groups is host time per step, not memory. Two changes need no regrouping: let Mamba2 use the precomputed state indices (about 420 µs per step on Granite, projected), and skip builds whose output a FULL decode graph does not read (20-65 µs per unsplit FlashInfer group).

What the heuristic does not know today, and a "build once per (backend, block size, policy), bind per group" design would need:

- a cost per builder and per group, so that splitting a bucket into equal-page groups is priced in host time per step and not only in padded bytes;
- each builder's graph support, so that one group's `NEVER` is visible before it removes FULL graphs for the whole model;
- builders that separate batch-level work (split, lengths, plan) from the bind (block-table pointer, slot mapping, state indices), so one build serves every group of a kind;
- a bind step that applies the kernel-block mapping (today's reuse path skips it, [`worker/utils.py:361-371`](https://github.com/vllm-project/vllm/blob/d33bfeef40edb158ddae320038737ee7923ad66f/vllm/v1/worker/utils.py#L361-L371)).

Each reader listed what its slice requires of any replacement. Merged and deduplicated:

1. **Declare each cache once, by its size law.** Per token, per n tokens with a rational ratio (compressed above 1, pooled below 1), or per request (recurrent state, rings, scratch). Exact bytes come from the object the kernel uses, so no probe or shadow planner re-derives them.
2. **State retention per kind as a function of position.** Full, window of `W − 1` plus retained tail, chunk, recurrent state plus snapshots at chosen positions, static sink (pinned for the pool's life), encoder span (fixed at admission, never prefix-cached). Frees follow the committed frontier.
3. **Share bytes only between pages of equal geometry.** Bounded objects (state, rings, drafter windows) are sized by their bound. Keep one registered range with stable virtual addresses, so FULL CUDA graphs and RDMA registrations survive commit, shrink, sleep and wake.
4. **Separate the hash unit from the allocation unit.** One content address (one hash chain at one unit) shared by the Rust and Python frontends, the engine, connectors and routers. A hit is valid where every kind can resume: all blocks for full attention, the window tail, the state at the boundary.
5. **One budget formula** for startup sizing, admission, per-step reservation and in-flight holds (draft scratch, async loads, copy-on-write), across every pool. "Not this step" is a distinct answer from "out of memory".
6. **Keep the boundary state of a shared prefix reachable.** Remember junction positions so their window tail or recurrent state is rewritten on the next pass, give blocks freed mid-request the recency of their request's end, and use one order for immediate and deferred frees. Measured: 87-112% of the hybrid hit-rate gap recovered, where evicting a prefix as one unit across kinds recovers 10-27%.
7. **Translate request position to page per policy, and null freed pages before any kernel reads them.** Block ids carry their group or state identity end to end, on the wire and in failure reports, so recovery recomputes one group's range.
8. **Build metadata once per step per (backend, kernel block),** with only page lists and state indices per group, capturable into FULL graphs. Scheduler cost must not grow with the number of kinds for a request that crosses no block boundary.
9. **One planner-owned byte descriptor per layer** (offset, strides, kernel split, payload against padding, pool), serializable, sent to and compared by peers once. Add a TP and DCP ownership law per cache (replicated, head-sharded, token-sharded) and a block-size law across TP.
10. **Kernels own the page interior** (K/V planes, records, inline scales) behind one injective format identity carried by the spec. Stride alignment is a declared requirement (16 B TMA, 512 B sparse SWA, 2 GiB pointer range), and the layout is chosen per allocation region, not per model.
11. **Drafters, KV-sharing aliases and PP stages without editing planner output afterwards.** A drafter's bounded cache can live in its own pool. One request-level rule covers the EAGLE drop and lookahead hashes for every kind and connector. Under PP each stage pays only for its own caches.
12. **Async safety.** No slot is reused before the device has finished writing it (the fence that [#67374](https://github.com/vllm-project/vllm/issues/67374) makes explicit), and no block is reachable from two kinds at once.
13. **One producer contract** that a model implements once and that fails at import or config time when a model implements the wrong method (bug 15), plus a block-table path for platforms without Triton, so the runner is not forked (the CPU runner is a 1,351-line fork, 78% identical).

The rungs fix the memory model, and nothing in this sweep argues against them. Four causes sit outside memory and stay open after rung 4.

- **Cause 4, block tables.** This is where the remaining silent bugs live (bugs 5 and 6; 66 historical bugs). A request table of virtual ids with per-pool translation once per step (SGLang) would make freed pages unreadable by construction.
- **Cause 5, the layout contract.** The planner already writes most of the descriptor, and SimpleCPU proves a connector can use it in 125 lines. What is missing is the peer: no PR sends the spec, and every TP-slicing PR scales the local one. The tpslice measurements price that guess (all four corruptions in [#67559](https://github.com/vllm-project/vllm/issues/67559)) and give the fix: each side sends, per page piece, an offset, named axes and a shard interval.
- **Cause 7, policy as data.** A declaration of lifetime and geometry per cache (TRT-LLM's lifecycle registry) would replace most of the 221 class tests and the overloaded hooks. It is also where the drafter's identity and the EAGLE rule belong.
- **Cause 8, metadata per group.** Even with one memory class, token kinds that differ in window or backend keep separate groups, and each costs a build per step. Building per (backend, kernel block) is a runner change that no rung covers.
